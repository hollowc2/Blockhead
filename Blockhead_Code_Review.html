Engineering review · TypeScript / Node.js · autonomous Mineflayer agent

Blockhead Code Review

Blockhead is not yet structurally reliable enough for unattended, multi-hour CobbleBob operation. The dominant risks are cancellation that does not reach Minecraft primitives, retry producers that recreate unchanged work, competing control of Mineflayer, and incomplete restart/reconnect recovery.

Review scope: README.md, Blockhead_v2_Implementation_Spec.md, package.json, config/, prompts/, and all code under src/. No repository code was modified during the review.

1. Executive Summary

189Passing tests

Passing tests establish useful unit-level behavior but do not establish autonomous runtime safety. The most likely multi-hour failures are:

  • an old skill keeps moving, collecting, fighting, or using a window after the scheduler times it out;
  • blocked maintenance work accumulates or is recreated with no changed conditions;
  • background container work conflicts with foreground inventory/crafting work;
  • bootstrap retries a permanently impossible stage forever;
  • a post-login Minecraft disconnect exits the process instead of reconnecting;
  • maintenance reports success without a measurable stockpile delta; and
  • llama.cpp unavailability leaves the active autonomous goal frozen.

3. Architecture Map

startup -> config loading -> SQLite migrations / repositories -> Minecraft connection -> Mineflayer plugins -> scheduler and task rehydration -> bootstrap / background maintenance -> chat command handling -> GoalManager / LLM decision -> tool dispatch and policy checks -> skills -> Mineflayer primitives and plugins -> result / failure handling -> task persistence and next scheduler decision

State ownership: scheduler owns task rows and the active-task reference; GoalManager owns the persisted autonomous goal; repositories own SQLite state; AgentState owns transient world/home knowledge; Mineflayer owns movement, windows, combat, and plugin state.

Ownership risks: bootstrap and background chest work can operate outside scheduler ownership; movement tools can call pathfinder directly; no global lease prevents competing Mineflayer operations; chat and background work can call the LLM concurrently; permanent failure decisions are split across dispatcher, watchdog, background cooldowns, bootstrap timers, and goal logic.

4. Critical Findings

Locations are source locations observed during review; line numbers may shift with later edits.

BH-001 — Timed-out skills continue running after scheduler failure

CriticalConfidence: High · Location: src/agent/dispatcher.ts:106-136, src/agent/skill-library.ts:195-209, src/agent/scheduler.ts:243-255

What happens: the dispatcher races a skill promise against a timeout and marks the task failed, but the underlying skill is not aborted. The scheduler can then start another task while the old run continues acting in the world.

Failure scenario: a collection task times out while pathfinding or collecting. The scheduler starts a home or combat task, while the old collector still moves or interacts. A stale signal lookup can also report the wrong cancellation state.

Recommended fix: give every skill an AbortSignal and require every Mineflayer primitive to stop on abort. Keep the task lease valid until the old operation has acknowledged shutdown; otherwise quarantine the bot from new world actions.

Test needed: start a fake long-running skill, trigger timeout/cancellation, assert pathfinder and listeners stop before another task may control the bot.

BH-002 — BLOCKED maintenance tasks accumulate without bound

CriticalConfidence: High · Location: src/agent/background.ts:147-165, 240-253, 320-334, src/agent/scheduler.ts:193-210, 350-389

What happens: a blocked background producer can run every second and insert another task. Cleanup prunes queued work but leaves blocked rows, so a missing prerequisite can create one persistent task per tick.

Failure scenario: no bed is available. Stockpile or bootstrap logic keeps attempting the same blocked work for ten minutes, leaving hundreds of persistent tasks and increasingly expensive scheduler scans.

Recommended fix: deduplicate by logical work key, persist a cooldown and failure fingerprint, cap blocked rows, and require a changed prerequisite or explicit operator reset before requeue.

Test needed: run the producer for a simulated hour with an impossible prerequisite and assert bounded task count and one recorded failure state.

BH-003 — Background container work bypasses scheduler serialization

High · src/agent/background.ts:235-317, src/agent/maintenance.ts:181-195, src/skills/containers.ts:80-105

Chest repair and stock measurement occur before the active-task gate and outside scheduler ownership. They can open windows, move items, or close containers while foreground crafting, storage, or recovery is operating.

Fix with one serialized world-action executor or a scheduler-owned resource lease covering windows, inventory, movement, and combat.

BH-004 — Movement tools directly own pathfinder state

High · src/tools/movement.ts:31-82, src/skills/movement.ts:80-165

LLM-facing movement tools can start pathfinder goals directly. Follow/home operations are fire-and-forget or otherwise lack a durable task lease, so a later skill can replace the goal or inherit active movement.

Fix by making movement a deterministic skill invoked only through task execution, with a single owner and completion/cancellation acknowledgement.

BH-005 — Hard cancellation does not propagate to all primitives

High · scheduler cancellation and skill/plugin call sites

Cancellation clears scheduler state and may stop pathfinder, but collectblock, PvP, crafting, container, and furnace operations can continue until their own timeout or event completion.

Fix explicit cancellation adapters for every plugin, listener cleanup, window close, combat disengagement, and a final “no active primitive” assertion before task replacement.

BH-006 — Maintenance deficit is interpreted as target inventory

High · src/agent/maintenance.ts:191-220, 266-313, collection/food runners

Maintenance computes “add N” but runners interpret quantity as desired carried count. Existing stock can therefore be deposited or treated as success without increasing total stock.

Fix define quantities as deltas at the maintenance boundary, verify before/after total stock, and only complete when the required net increase is present.

BH-007 — Goal cancellation leaves queued goal tasks behind

High · GoalManager cancellation and goal task cleanup

GoalManager.cancel does not call the task cancellation path used for replacement. Queued, paused, or blocked tasks from the cancelled goal can remain and later execute.

Fix make cancellation a single idempotent operation that marks the goal, cancels every owned task, and records the cancellation reason transactionally.

BH-008 — Bootstrap retries impossible stages forever

High · bootstrap retry loop

After three attempts, bootstrap continues every 30 seconds with no durable attempt history, exponential backoff, changed strategy requirement, or terminal failure state.

Fix persist stage attempts and failure codes, use bounded exponential backoff, and require a changed world condition or operator intervention after the retry budget is exhausted.

BH-009 — Detached bootstrap rejection can become an unhandled rejection

High · bootstrap startup and executeWithRetries; furnace opening is a concrete throw path

Bootstrap is launched with void run(); stage exceptions are not guaranteed to be converted to durable task failure. An ordinary plugin/window error can therefore become a process-level failure.

Fix top-level supervision that catches every detached promise, records the failure, and transitions bootstrap to a recoverable state.

BH-010 — Post-login disconnect exits instead of reconnecting

High · Minecraft connection lifecycle

Initial connection retries exist, but after a successful spawn a disconnect closes resources and calls process.exit(1). A two-minute Eros restart therefore requires an external supervisor or manual restart.

Fix a connection state machine with bounded reconnect backoff, task interruption/reconciliation, plugin reinitialization, and safe resumption after spawn.

BH-011 — No process-wide LLM single-flight or robust tool repair

Medium · chat/background LLM call sites and decision dispatch

Concurrent callers can receive out-of-order responses. Invalid tool names and arguments are rejected downstream without a structured repair decision, allowing repeated identical prompts.

Fix a bounded LLM request queue, schema validation before dispatch, invalid-action feedback, and per-goal repeated-decision suppression.

BH-012 — LLM outage freezes the active autonomous goal

High · GoalManager decision loop

LLM failure is caught as handled, but no deterministic fallback, pause reason, or retry policy advances the goal. A llama.cpp outage can leave it apparently alive but inactive.

Fix bounded backoff, explicit PAUSED/DEGRADED state, deterministic safe actions such as retreat/idle, and recovery on LLM health restoration.

BH-013 — Execution paths bypass stronger policy checks

High · src/policy/ and collection/placement execution paths

Strong block destruction/placement checks are used in tests but not consistently at execution. Explicit collection can bypass protected-home infrastructure checks; placement guards are incomplete. Defense checks health once and uses a hardcoded threshold.

Fix policy enforcement immediately before each destructive action, with current-world revalidation and configured thresholds.

BH-014 — Death recovery state is memory-only

High · death coordinator

Pending death IDs, recent deaths, and the loop brake disappear on restart. A crash between death and respawn loses the recovery workflow; restart also clears the anti-loop protection.

Persist death lifecycle and reconcile it against current spawn/health on startup.

BH-015 — SQLite permits multiple ACTIVE tasks and trusts persisted JSON

Medium · task schema/rehydration and startup parsing

Multiple ACTIVE rows can exist. Rehydration overwrites the active reference, orphaning earlier rows. Malformed persisted JSON can crash startup.

Add database constraints or transactional reconciliation, tolerant parsing with quarantine, and startup diagnostics for repaired state.

BH-016 — Partial build success can complete a task with no world change

High · base/build skill result handling

The base skill can return ok=true after partial or zero placement. The dispatcher completes the task and the watchdog may treat the result as progress, causing immediate recreation of the same unfinished work.

Require measurable before/after world deltas and distinguish COMPLETE, PARTIAL, and FAILED outcomes.

BH-017 — ensure_item has incorrect dependency and quantity semantics

High · src/skills/ensure-item.ts and collection/crafting dependencies

Raw-meat requests can call a generic food runner and credit the requested item without verifying it. Partial coal can be credited as full. Missing furnace asks for stone instead of cobblestone. Bulk success does not require deposit.

Use item-specific recipes and acquisition strategies, verify exact inventory deltas, and detect dependency cycles before execution.

BH-018 — Container accounting reports success without transfer

Medium · src/skills/containers.ts

Withdraw can return total carried rather than delta; transfer math uses remaining source totals; giving to an absent player and retrieving nothing can still report success.

Verify actor/container/item counts before and after every transfer and require the requested delta.

BH-019 — Cached llama model ID survives server model changes

Medium · LLM client model discovery/cache

The model ID is cached for the process lifetime. If llama.cpp changes models or returns a 4xx, the client does not invalidate and rediscover, so recovery requires restart.

Invalidate cache on model-related errors and re-probe with bounded backoff.

BH-020 — Logs cannot explain a fifteen-minute standstill

Medium · logging and task history

Logs do not consistently expose phase, primitive, progress age, retry count, pathfinder state, open window, last successful action, or relevant health/inventory state. Histories/logs also lack retention controls.

Add structured task/skill/primitive events, a periodic heartbeat, progress fingerprints, and bounded retention.

6. Scheduler Findings

  • Task states exist, but ownership and cancellation are distributed across scheduler, dispatcher, background producers, and GoalManager.
  • ACTIVE tasks can be orphaned by rehydration and multiple ACTIVE rows are not prevented at the database boundary.
  • PAUSED/BLOCKED tasks have no uniform resume owner or durable reason-to-resume condition.
  • Cancellation can race completion; completion must verify task identity, generation, and cancellation status transactionally.
  • Foreground starvation is possible when background work is inserted outside scheduler serialization.
  • Queues have no clearly enforced global bound or logical-key deduplication.

8. LLM Integration Findings

  • HTTP failure, empty output, prose, malformed JSON, invalid tool names, invalid argument types, and hallucinated items are not all converted into durable state-machine outcomes.
  • There is no process-wide single-flight queue, so chat and autonomous decisions can overlap.
  • Policy rejection does not reliably provide a changed observation to the next decision.
  • Active goals lack a deterministic degraded mode when llama.cpp is offline or slow.
  • Deterministic checks should handle prerequisites, item existence, inventory deltas, and safe fallback movement; the model should select intent rather than mechanically drive Minecraft.

9. Mineflayer / Async Findings

  • travelAndWait has a useful path timeout and abort polling, but equivalent guarantees are not present across all primitives.
  • Listeners, timers, windows, combat targets, and pathfinder goals need explicit lifecycle ownership.
  • Operations resolving after cancellation can mutate state belonging to a replacement task.
  • Generic timeout helpers should clear their timer when the operation wins; otherwise long-running sessions accumulate timer pressure and delayed callbacks.

10. Persistence / Restart Findings

  • Positive foundations include WAL mode, foreign keys, transactional migrations, and synchronous repository writes.
  • Persisted knowledge such as chest locations, bed completion, and storage assumptions can become stale relative to the Minecraft world and must be verified.
  • Task, goal, home, storage, site, and watchdog state partially survive restart, but primitive state, bootstrap retry state, goal cooldown, death pending state, and pathfinder/window state do not.
  • The implementation does not provide a complete crash-cut-point reconciliation protocol for bootstrap, crafting, smelting, travel, maintenance, or death recovery.
  • History/log tables have no clear retention or rotation strategy.

11. Observability Findings

To diagnose “CobbleBob has been standing still for 15 minutes,” logs need a structured heartbeat containing:

  • task ID, logical work key, task age, state, priority, and owning goal;
  • skill, phase, primitive, progress timestamp, attempt number, and last failure code;
  • position, health, hunger, inventory fingerprint, pathfinder goal/status, open window, and combat target;
  • last LLM request ID, latency, response classification, tool selection, and policy decision; and
  • scheduler queue size, active lease owner, paused/blocked reason, and reconnect state.

12. Test Coverage Gaps

  • Real or faithful async cancellation of pathfinder, collectblock, PvP, container, furnace, and auto-eat operations.
  • Timeout followed by replacement task, proving the old operation cannot continue.
  • Blocked producer soak test proving bounded task count.
  • Concurrent LLM calls and malformed/slow/offline llama.cpp responses.
  • Multiple ACTIVE rows, corrupt JSON, crash recovery at every important task boundary.
  • Post-spawn Minecraft disconnect and server restart recovery.
  • Net inventory/stockpile delta tests for maintenance, ensure_item, crafting, storage, and building.
  • Dynamic policy revalidation after world changes.
  • Listener/timer/window leak tests and multi-hour simulated soak tests.

14. Recommended Fix Order

  1. Implement cancellation propagation and primitive ownership. Make every skill cancellable and prevent replacement until the old Mineflayer operation stops. This removes the highest-risk world corruption and task-fighting behavior.
  2. Add a per-task lease and generic progress watchdog. Track phase, progress fingerprint, timeout, attempts, and failure code. This creates a common end condition for every skill.
  3. Deduplicate and bound background/maintenance work. Use logical work keys, durable cooldowns, and blocked-task limits before fixing higher-level strategy.
  4. Make result verification delta-based. Inventory, stockpile, placement, transfer, and crafting success must be measured before/after; partial work must not become success.
  5. Serialize all world actions through the scheduler or resource leases. Remove direct competing container, pathfinder, and combat ownership.
  6. Build a supervised connection state machine. Reconnect Minecraft and llama.cpp with backoff, interruption, reinitialization, and safe resumption.
  7. Harden persistence/restart reconciliation. Enforce one active task, quarantine malformed rows, persist death/bootstrap lifecycle, and verify stale world knowledge.
  8. Harden the LLM boundary. Add schema validation, single-flight requests, bounded retries, invalid-action feedback, and deterministic degraded behavior.
  9. Enforce policy at the final action boundary. Revalidate current world state immediately before destructive or dangerous actions.
  10. Add soak and fault-injection tests plus structured heartbeat logging. Only after the preceding controls exist will long-running tests distinguish slow progress from stuck behavior.

15. Top 10 Regression Tests

  1. Timed-out collection skill cannot move, collect, or emit a late completion after replacement.
  2. Cancellation closes windows, stops pathfinder/combat, removes listeners, clears timers, and releases the task lease.
  3. Impossible maintenance prerequisite produces one bounded blocked record rather than unbounded rows.
  4. Maintenance deficit increases total stock by the requested delta and does not pass using pre-existing inventory.
  5. Partial build/transfer/craft result is PARTIAL or FAILED, never successful without measurable delta.
  6. Two simultaneous foreground/background world actions are serialized or rejected with a clear owner conflict.
  7. llama.cpp offline/slow/malformed/invalid-tool responses enter degraded mode without crashing or repeating forever.
  8. Minecraft disconnect after spawn reconnects, reinitializes plugins, reconciles the active task, and resumes safely.
  9. Restart with multiple ACTIVE tasks, malformed JSON, pending death, or incomplete bootstrap repairs/quarantines state deterministically.
  10. Multi-hour simulated soak with an unreachable target proves bounded queue size, bounded retries, no listener/timer leaks, and useful heartbeat diagnostics.

Bottom line: the architecture is directionally sound—LLM intent, deterministic skills, Mineflayer primitives—but the runtime lacks the cancellation, ownership, progress, reconciliation, and supervision guarantees required for unattended operation.
